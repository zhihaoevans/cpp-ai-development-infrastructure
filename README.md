# C++ 项目 AI 自动化开发基础设施

> 为 C++ 项目建立可理解、可构建、可验证、可追溯的工程基础，让人和 AI 编码代理都能可靠地开发。

## 为什么需要这些基础设施

AI 能快速修改代码，但如果项目缺少明确需求、稳定的构建入口和自动化反馈，它也难以判断修改是否正确。基础设施的目标是形成闭环：**任务定义 → 获取上下文 → 实现 → 本地验证 → CI 验证 → 人工审查 → 合并与观测**。

本仓库定位为建设指南，而非宣称一套工具适用于所有项目。优先保证可重复构建和真实有效的测试，再逐步引入高级自动化。

## 基础设施地图

| 层次 | 要解决的问题 | 最小交付物 | 完成标准 |
|---|---|---|---|
| 项目上下文 | AI 如何理解项目？ | README、架构图、目录说明、AGENTS.md | 新成员可找到入口、约束、验证命令 |
| 需求与设计 | 怎么定义正确行为？ | Issue 模板、验收标准、接口契约、ADR | 每项变更有可检查的结果和边界 |
| 可重复环境 | 换台机器能否构建？ | 固定工具链、依赖版本、开发容器或脚本 | 干净环境按文档完成构建与测试 |
| 构建与依赖 | 如何快速定位与编译？ | CMake Presets、依赖清单、compile_commands.json | 单条命令配置构建；版本受控 |
| 质量反馈 | 修改如何证明正确？ | 测试、格式检查、静态分析、Sanitizer | 本地及 CI 失败时返回非零退出码 |
| 交付与协作 | 怎样审查并安全合并？ | PR 模板、CI 检查、分支保护 | 审查者可看到变更、风险与验证结果 |
| 运行与诊断 | 出问题如何复现？ | 结构化日志、指标、错误码、故障复现步骤 | 能将异常定位到版本与输入 |
| AI 工作约束 | AI 能做什么、不能做什么？ | AGENTS.md、最小权限、任务模板 | 边界、敏感信息和验证流程清晰 |
| 持续评估 | 自动化是否真的带来价值？ | 基线指标、失败案例与复盘 | 用数据跟踪反馈速度及缺陷 |

## 优先建设顺序

### P0：让项目能够可靠修改

- [ ] README 写明支持的平台、依赖、构建、测试、运行与常见故障。
- [ ] 统一编译器、C++ 标准、构建类型及第三方依赖版本；记录环境差异。
- [ ] 提供 `CMakePresets.json`，生成 `compile_commands.json`，支持增量构建。
- [ ] 给核心行为建立单元测试与回归测试；新增缺陷先保留复现用例。
- [ ] CI 在提交和 PR 时执行与本地一致的构建、测试及格式检查。
- [ ] 用 `AGENTS.md` 记录真实命令、项目边界、目录和不可破坏的约束。
- [ ] 配置 PR 审查和必要的保护规则；AI 给出证据，人负责高风险决策。

### P1：提高自动反馈质量

- [ ] 使用 clang-format、clang-tidy 等工具，明确版本和规则。
- [ ] 在适用平台分别运行 ASan/UBSan；并发代码考虑单独运行 TSan（通常不能与 ASan 同时启用）。
- [ ] 对公开接口、协议解析、错误处理和边界输入建立集成测试。
- [ ] 建立缓存、并行构建和测试分层，记录耗时，保持反馈及时。
- [ ] 整理模块边界、线程模型、对象所有权和关键设计决策。
- [ ] 对依赖变更、漏洞、许可证和供应链风险建立审查流程。

### P2：面向复杂工程和规模化协作

- [ ] 使用 fuzzing 测试不可信输入；保存崩溃样本并转换为回归用例。
- [ ] 对性能敏感路径建立基准、运行环境和基线；对显著波动复测。
- [ ] 根据项目需要接入覆盖率、SBOM、制品签名和发布回滚。
- [ ] 收集代理任务成功率、人工返工、缺陷逃逸和 CI 反馈时间。
- [ ] 建立真实任务评测集，避免仅根据代码生成速度判断效果。

## 推荐目录

```text
README.md                  项目入口与快速开始
AGENTS.md                  代理可执行的项目约束
CMakeLists.txt             构建定义
CMakePresets.json          统一配置、构建和测试入口
.clang-format              格式规范
.clang-tidy                静态分析规则
docs/architecture.md       模块、依赖、线程和数据流
docs/decisions/            架构决策记录（ADR）
src/ include/              实现与公共接口
tests/                     单元、集成和回归测试
benchmarks/                可重复的性能基准
scripts/                   本地与 CI 共用的检查入口
.github/workflows/         CI 工作流
.github/ISSUE_TEMPLATE/    需求和缺陷模板
.github/PULL_REQUEST_TEMPLATE.md
```

以上是建议结构，不要求所有项目立即创建全部目录。

## C++ 的关键工程风险

- **内存和生命周期**：明确所有权、借用关系和异常安全；结合 RAII、ASan、代码审查验证。
- **并发**：说明线程归属、锁顺序和共享数据；TSan 只能发现被测试覆盖到的部分问题。
- **构建和 ABI**：记录编译器、标准库、编译选项、ABI 与目标平台；避免本地和 CI 配置漂移。
- **未定义行为**：利用编译警告、UBSan 和边界测试，但不要把工具通过当作正确性的证明。
- **依赖与安全**：固定来源和版本，审查新增依赖；不将密钥、真实客户数据或内部日志暴露给未授权的代理。
- **性能**：明确吞吐、延迟、内存和环境；将微基准结果与实际负载分开解释。

## 可复制的 AGENTS.md 模板

根据项目实际情况填写并测试，保持简短；不要复制未经验证的命令。

```markdown
# 项目说明
- 目标：<项目用途>
- 主要目录：<目录及职责>
- 支持平台、编译器、C++ 标准：<实际版本>

# 开发与验证
- 配置：<实际命令>
- 构建：<实际命令>
- 测试：<实际命令>
- 格式与静态分析：<实际命令>
- 无法运行检查时，说明原因及替代验证。

# 约束
- 保持公开接口和兼容性，除非任务明确要求变更。
- 修改所有权、线程、协议、性能关键路径时，补充相应验证。
- 不提交密钥、生成文件或未经审查的第三方代码。
- 提交结果说明改动、测试、风险和未完成事项。
```

## 任务模板

```markdown
### 背景与问题
<现象、业务目标、复现方式>
### 范围与约束
<涉及模块、不包含的内容、兼容性和性能要求>
### 验收标准
- [ ] <可观察的行为>
- [ ] <错误及边界情况>
### 验证
<测试命令、数据、预期结果>
### 风险
<并发、生命周期、ABI、安全、回滚>
```

## 首次落地示例：网络流量解析器

针对 Linux 网络和高性能 C++ 项目，可从一个小型流量解析器开始：

1. 固定编译工具链，提供 CMake 构建、测试命令及最小示例输入。
2. 用合法、截断、畸形输入验证解析结果；把故障样本保存在测试集中，去除敏感数据。
3. CI 运行普通构建与 ASan/UBSan，独立配置并发测试和 TSan。
4. 补充模块边界、buffer 所有权、线程模型以及输入大小限制。
5. 用固定数据和环境测吞吐、延迟；涉及 DPDK、网卡、NUMA 或 hugepages 时，另设有条件的专用环境，不把普通 CI 通过视为真实硬件性能验证。
6. 给代理一个小任务，例如支持一种报文头字段；验收包含正确、截断和错误输入，并记录运行结果。

## 完成的定义

一项变更至少应具备：明确需求和验收标准、可审查的代码、适当的自动化验证、失败情况说明、CI 结果及必要的人工审查。对性能、并发、兼容性和安全敏感的改动，还应给出对应证据；不能执行的检查必须说明限制。

## 后续建设路线

1. 补充逐项指南：环境、CMake、依赖、测试、CI、AI 上下文、安全与可观测性。
2. 构建可运行的 C++ 示例项目，验证本地和 CI 使用相同入口。
3. 添加协议解析案例、模糊测试、性能基准以及真实任务评测。
4. 根据项目实践记录故障、权衡和实际指标，持续修订。
