# 测试与质量保障

## 验证分层

| 层次 | 主要关注 | 示例 |
|---|---|---|
| 单元测试 | 清晰且确定的行为与边界 | 解析正常头、截断和无效长度 |
| 集成测试 | 模块协作与外部依赖 | 从输入读取、解析并输出结果 |
| 回归测试 | 已出现过的缺陷 | 保存去敏后的最小触发输入 |
| 系统测试 | 实际部署环境 | 硬件、系统配置及端到端流量 |
| 性能测试 | 延迟、吞吐、资源消耗 | 固定输入、机器配置和基准版本 |

## C++ 工具链

- 警告和静态分析：启用适合项目的编译器警告、clang-tidy；逐步治理历史告警，避免只追求零告警而关闭有效规则。
- 内存和未定义行为：在适用平台使用 ASan 和 UBSan；在有代表性的输入上运行。
- 并发：单独构建 TSan，不与 ASan 混用；覆盖重要线程交错，工具不能证明无竞态。
- Fuzzing：优先覆盖不可信输入；限制运行资源，保留最小崩溃样本作为回归测试。
- 性能：记录 CPU、NUMA、编译器、选项、负载和样本分布；不把 CI 虚拟机结果当作生产硬件结论。

## CI 验收

新变更先跑格式、编译、单测等快速检查，再按成本安排 sanitizers、集成与系统测试。CI 应在检查失败时失败；外部资源不可用时报告为未验证而非通过。不要使用带有写权限或密钥的上下文运行不可信的 PR 代码。

## 本仓库已启用的检查

当前 CI 包含 Debug 构建、CTest、clang-format 18 与 clang-tidy 18 选定规则检查。本地执行相同的 `scripts/check_quality.py` 入口，安装和命令见[编码规范](coding-standards.md)。所有检查失败时返回非零状态；格式检查不会自动修改文件。Sanitizer、fuzzing、性能测试和纯 C 编译是上述建设建议，尚未接入当前 CI。
